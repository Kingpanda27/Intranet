1. Introducción & Visión General del Sistema

1.1 Nombre y Propósito Corporativo

La Intranet Corporativa de Telecom Networks es una plataforma de software empresarial concebida como el epicentro digital y operativo de la organización. Su propósito central es brindar a todos los colaboradores, supervisores y equipos ejecutivos un espacio seguro, intuitivo y colaborativo que simplifique la autogestión de solicitudes laborales, la consulta de normativas internas, el reporte de incidencias técnicas en teletrabajo y la comunicación organizacional de alto impacto.

1.2 Objetivos Estratégicos

  • Unificación Operacional: Eliminar el uso fragmentado de hojas de cálculo aisladas, chats informales y correos dispersos para la solicitud de ausencias y aprobaciones de turnos.
  • Soporte Proactivo y Diagnóstico Guiado: Asistir a los colaboradores que realizan teletrabajo mediante el agente inteligente Soporte AILlama con metodología progresiva en 3 niveles y resolución de emergencias técnicas.
  • Gobernanza de Datos y Seguridad: Implementar un modelo de control de acceso basado en roles (RBAC) con aislamiento por escuadrón (Row-Level Authorization) y trazabilidad inmutable mediante logs de auditoría en tiempo real.
  • Transparencia Directiva: Facilitar a managers y recursos humanos reportes dinámicos, exportación de nómina a CSV compatible con Microsoft Excel y visualización de indicadores clave (KPIs) en tiempo real.

2. Arquitectura General & Stack Tecnológico

La plataforma adopta una topología de capas desacopladas que garantiza alta concurrencia, respuesta inmediata en milisegundos y resiliencia ante contingencias externas de red o caídas de servicios de terceros.

2.1 Diagrama de Arquitectura de Sistemas y Flujos de Datos

+---------------------------------------------------------------------------------------+ | CAPA DE CLIENTE / NAVEGADOR | | - Plus Jakarta Sans Typography - Glassmorphism & Tokens HSL | | - Formularios Reactivos React 19 - Streaming SSE (Chat en Tiempo Real) | +-------------------------------------------+-------------------------------------------+ | Peticiones HTTPS | Server Actions & REST API v +---------------------------------------------------------------------------------------+ | CAPA DE APLICACIÓN Y PERÍMETRO (NEXT.JS 15) | | - middleware.ts: Verificación perimetral, expiración de sesión y control de acceso | | - Server Actions: timeOffActions, userActions, groupActions, auditActions | | - Route Handlers: /api/chat (SSE Stream), /api/requests/* (IDOR Shield) | +-------------------+-----------------------+--------------------+----------------------+ | | | Consultas SQL | Caché Sesión | Streaming SSE | Fallback Auto vía Prisma | y Snapshots | | v v v v +------------------------+ +-------------------+ +--------------------+ +--------------------+ | BASE DE DATOS MYSQL | | REDIS 7.X | | NVIDIA NIM API | | OLLAMA LOCAL | | - Usuarios & Roles | | - Sesiones Rápidas| | - Llama 3.2 11B | | - Instancia local | | - 12 Tipos Permisos | | - Throttling | | - Streaming SSE | | en puerto 11434 | | - Historial Auditoría | +-------------------+ +--------------------+ +--------------------+ | - Índices Collation | +-----------+------------+ ^ | Sincronización Solo Lectura (SELECT) +-----------+------------+ | WFM PLATFORM MYSQL | | - 49 Grupos DeskTime | | - 274 Empleados | +------------------------+

2.2 Componentes Esenciales del Stack

  • Capa de Presentación: Renderizado reactivo en Next.js 15.1 con TypeScript y soporte nativo para temas claro y oscuro mediante tokens variables HSL. El sistema de diseño no requiere utilidades externas pesadas, garantizando una carga veloz y libre de dependencias no controladas.
  • Capa de Lógica Transaccional (Server Actions): Todas las mutaciones de datos se ejecutan en el servidor mediante funciones tipadas seguras con control de acceso por sesión, eliminación de riesgo CSRF y manejo transaccional de excepciones.
  • Persistencia de Datos (MySQL 8.x): La base de datos opera bajo el motor InnoDB con transacciones ACID, soporte nativo de collation utf8mb4_unicode_ci e índices en campos de búsqueda rápida (nombres, correos, estados y tipos de solicitud).
  • Sincronización Externa WFM (DeskTime): Integración unidireccional de solo lectura con la base de datos wfm_platform, manteniendo homologados en tiempo real los 49 grupos corporativos y los 274 colaboradores de la organización.
  • Arquitectura de Inteligencia Artificial Dual: Inferencia primaria en la nube de NVIDIA NIM con respuesta inmediata en streaming y conmutación transparente hacia Ollama local si la API externa experimenta degradación de red.

3. Modelo de Seguridad, RBAC y Data Scoping

La Intranet implementa un modelo de seguridad por capas que combina autenticación criptográfica basada en cookies HTTP-only, control de acceso basado en roles jerárquicos (RBAC) y autorización a nivel de fila (Row-Level Authorization / Data Scoping) para prevenir accesos indebidos e IDOR.

3.1 Jerarquía Numérica de Roles

Cada rol dispone de un nivel jerárquico entero que regula la subordinación, privilegios y protección de cuentas:

NO_ROLE (0) < USER / AGENT (10) < SUPERVISOR / TEAM_LEAD (20) < MANAGER (30) 
            < HR (35) < TECHNOLOGY (40) < IT_MANAGER / TECHNOLOGY_ADMIN (50) < DIRECCIÓN / SUPERADMIN

3.2 Matriz Exhaustiva de Permisos

3.3 Mecanismos de Aislamiento y Protección (Data Scoping & IDOR)

🛡️
Protección IDOR / BOLA (Insecure Direct Object References): Ninguna solicitud puede ser aprobada o rechazada mediante el simple conocimiento de su identificador ID. La función authorizeRequestAction() valida en la base de datos que el usuario solicitante sea supervisor legítimo del colaborador mediante las tablas relacionales de escuadrones antes de autorizar cualquier cambio de estado.
  • Cláusula Dinámica de Alcance (getTimeOffScopeFilter): Al consultar solicitudes de tiempo libre en el panel de control, el sistema intercepta la llamada SQL. Para supervisores y líderes, aplica un filtro restrictivo: userId IN managedUserIds, aislando los datos y garantizando que ningún supervisor pueda ver solicitudes de escuadrones ajenos.
  • Acceso Exclusivo a Configuración TI (canAccessITConfig): Módulo restringido exclusivamente al personal de Tecnología y administradores autorizados. Si un colaborador de Recursos Humanos, supervisor o empleado común intenta acceder a /configuracion-ti o /admin/config, el servidor intercepta la petición y redirige a la página segura /acceso-denegado.
  • Salvaguarda Jerárquica de TI: Los usuarios con rol TECHNOLOGY pueden eliminar usuarios regulares, pero tienen vedada la eliminación de cualquier miembro del equipo de Tecnología, facultad reservada de forma estricta para el IT_MANAGER o superadministradores autorizados.

4. Instalación, Configuración y Variables de Entorno

4.1 Requisitos de Infraestructura

  • Servidor Host Recomendado: Debian 12 (Bookworm) o Ubuntu 22.04 LTS (x86_64).

5.2 Filosofía de Desarrollo: Server Actions vs. API Routes

  • Server Actions (app/actions): Empleadas de manera preferencial para todas las mutaciones de interfaz (solicitudes de tiempo libre, cambios de miembros de grupo, actualización de perfiles y creación de usuarios). Garantizan validación en el servidor sin serialización insegura de parámetros.
  • Route Handlers (app/api): Reservados para flujos con streaming continuo de datos (Server-Sent Events en app/api/chat/route.ts), integración de webhooks entrantes de WhatsApp o consumo externo desde servicios satélites.
  • Tokens HSL de Diseño: No se utilizan librerías CSS invasivas que distorsionen el rendimiento. Toda la interfaz consume variables HSL nativas (--primary, --surface, --background) con soporte para desenfoques de fondo (backdrop-filter: blur(12px)).

  • Búsqueda Multi-Tabla Exhaustiva: Detección automática de intenciones y consulta directa sobre MySQL para responder con precisión sobre:
    • Colaboradores y Balances: Encuentra a cualquier colaborador por nombre o apellido y responde con su cargo, grupo y balance de días de vacaciones disponibles.

  • Reconocimiento de Autorización Maestra: Reconoce tanto a los roles de alta dirección (CEO / Director) como a Iván Reyes (Desarrollador de AI & Software Development con credenciales maestras de soporte), entregando respuestas ejecutivas con cifras exactas sin evasivas de derivación a Recursos Humanos.
  • Streaming SSE con Tolerancia a Fallos: Motor primario en NVIDIA NIM Cloud API (meta/llama-3.2-11b-vision-instruct) y conmutación automática hacia Ollama local si la nube externa no responde.

Soporte AILlama L1 (Asistencia Técnica para Teletrabajo)

  • Metodología de Diagnóstico en 3 Intentos: Nivel Físico (inspección de cables) → Nivel Aplicación (limpieza de navegador) → Nivel Sesión (modo incógnito o reseteo guiado).
  • Política de Cero Fricción: Prohibido sugerir comandos de consola (CMD, PowerShell, ping), reinicios forzados de PC o alteraciones en el BIOS.
  • Escalación Automática a L2: Al completarse el tercer intento sin resolución, genera automáticamente un registro en SupportTicket y despacha una notificación por correo a Helpdesk.
  • Soporte Bilingüe Interactivo: Selector de idioma en tiempo real (Español / English).

7. Administración y Operaciones del Sistema

La plataforma opera bajo el gestor de procesos PM2 en servidores Linux, respaldado por un proxy inverso Apache en el puerto 80 que canaliza el tráfico seguro hacia la instancia Node.js en el puerto 3000.

  • Gestión de Sesiones JWT: Sesiones encriptadas con caducidad configurable y rotación automática de credenciales.
  • Servidor de Notificaciones SMTP: Conectividad TLS autenticada con Exchange Online / Microsoft 365 para despacho de correos transaccionales a supervisores y colaboradores.

8. Mantenimiento y Solución de Problemas (Troubleshooting)

Incidencia Detectada Causa Raíz Típica Acción Correctiva Recomendada
La intranet no responde en el navegador Servicio Node.js detenido o Apache caído Ejecutar pm2 status y systemctl status apache2. Reiniciar con pm2 restart intranet.
Error P1001 en Base de Datos Servicio MySQL detenido o credencial incorrecta Comprobar systemctl status mysql y verificar la variable DATABASE_URL en .env.local.
TN Assistant indica que la IA no responde Falta de conexión con NVIDIA API y Ollama apagado Revisar NVIDIA_API_KEY en Configuración TI y validar Ollama local con ollama list.
Modificaciones en estilos no impactan Caché estática de Next.js persistente Purgar el directorio: rm -rf .next/cache, recompilar con npm run build y recargar PM2.

9. Políticas de Respaldo, Restauración y Disaster Recovery

⚠️
Estrategia de Respaldos Diarios:
  1. Base de Datos MySQL: mysqldump -u root -p --single-transaction --routines --triggers --events intranet > /backups/intranet_$(date +%F).sql
  2. Directorio Uploads: tar -czf /backups/uploads_$(date +%F).tar.gz public/uploads/
  3. Caché Redis: Copia periódica del archivo de snapshot dump.rdb.

10. Buenas Prácticas de Desarrollo y Despliegue

  • Despliegues Zero-Downtime: Utilizar pm2 reload intranet en producción para renovar trabajadores sin pérdida de sesiones.
  • Seguridad OWASP Mandatoria: Toda Server Action debe comprobar la sesión y ejecutar authorizeRequestAction antes de alterar registros.
  • Coherencia de Diseño: Emplear exclusivamente tokens HSL y clases universales (.card, .glass, .btn-primary) definidas en DESIGN_SYSTEM.md.
